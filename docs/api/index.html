REST API for managing data connections and connection types.

Authentication

All endpoints except /health require a bearer token. All endpoints except /health and /audit/data-connection-types additionally require the x-tenant-id header.

A missing or invalid token returns 401, and a token that lacks permission for the requested operation returns 403. A missing or empty x-tenant-id header is a request validation failure and returns 400, not 401; a well-formed header naming a tenant you cannot access returns 403.

1. Obtain a token

For your own user:

export user_token=$(oc whoami -t)

For a ServiceAccount, bind the audience the service expects:

export user_token=$(oc create token <sa-name> -n <namespace> \
  --audience="$(oc get authentication cluster -o jsonpath='{.spec.serviceAccountIssuer}')" \
  --duration=1h)

The token audience must match the DataConnectService CR's configured spec.tokenReviewAudiences; a mismatch returns 401 unauthenticated. The list is empty by default, in which case the cluster API server's own audience applies.

2. Send the request

export TENANT_NAMESPACE=dch-example

curl -H "Authorization: Bearer $user_token" \
     -H "x-tenant-id: $TENANT_NAMESPACE" \
     https://dch-rest-dch-services.apps.example.com/api/v1alpha1/data/connections

connections

A connection binds a connection type to credentials stored in a Kubernetes secret and connector-specific properties. Connections are tenant-scoped and require the x-tenant-id header. On create, supply credentials via credentials_ref (reference an existing secret) or credentials (the server creates the secret). On patch, use credentials_ref to point at a different secret; inline credentials in the patch body are silently ignored. The status.state field reflects live connection health. Call /connections/{id}/readiness to refresh it.

Create a connection

Creates a connection that binds a connection type to credentials and connector-specific properties. The referenced connection type must already exist. Use /test/credentials to validate credentials before creating a connection. Returns 400 with credentials_check_failed when inline credentials do not satisfy the connection type schema. For inline credentials, a missing connection type returns 404; for a credentials_ref, it returns 422. Accepts two payload variants (untagged union): use credentials_ref to reference an existing secret, or credentials to supply inline credentials (the server creates the secret automatically).

Check connection readiness

Validates that the connection's credentials secret exists, matches the connection type schema, and that the data source is reachable. Updates the connection status accordingly. When a credentials secret cannot be read, fails schema validation, or the data-source check fails, the connection status is updated before the error is returned. A missing connection returns 502 without a status update. Returns 400 with invalid_secret or credentials_check_failed when the secret is missing or does not match the connection type schema. Returns 502 with connection_check_failed when the connection is not found or the data source check fails. Returns 500 with status_update_failed when the service cannot persist an updated connection status.

connection-types

A connection type defines a schema for a data connection. A connection type must be created before creating a connection of that type. Connection types are typically created by the Data Connect Hub operator, but you can also create your own custom connection types. Connection types created by the operator are known as global connection types and are accessible by all tenants. Connection types created by a tenant are only accessible by that tenant.

List connection types

Returns all connection types that are accessible to the tenant. This includes global connection types created by the operator and any custom connection types created by the tenant.
